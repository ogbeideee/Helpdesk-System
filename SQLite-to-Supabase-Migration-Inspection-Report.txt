3. SQLITE -> POSTGRESQL COMPATIBILITY ISSUES
--------------------------------------------------------------------------------

BLOCKING / MUST FIX
  1. schema.prisma provider "sqlite" -> "postgresql" (+ add directUrl).
  2. migration_lock.toml provider "sqlite" + the single SQLite-flavored
     migration - unusable on PG; a fresh Postgres baseline is required.
  3. scripts/lib/testdb.js - "file:" URLs and journal/WAL file cleanup are
     SQLite-only.
  4. scripts/test-assignment-groups.js pragma_table_info query -
     PG-incompatible.

COMPATIBLE BUT WORTH NORMALIZING
  5. ensureSingleLeadIndex raw SQL works on PG, but should move into the
     baseline migration; be aware "db push" doesn't know this index and may
     flag drift (it is exactly what the current codebase relies on after
     every push).

RUNTIME BEHAVIOR DIFFERENCES TO EXPECT AFTER THE SWITCH
  a. WRITE CONCURRENCY: SQLite serializes writers process-wide; PostgreSQL is
     truly concurrent. nextTicketNumber's upsert is atomic on both, but
     concurrent ticket creation on PG can surface Prisma P2034 / serialization
     errors or unique-violation timing that never appeared on SQLite (no retry
     logic exists today; transactions use default isolation, no isolationLevel
     specified). The handover "pending limit" check-then-create inside
     $transaction relies on the transaction; under Read Committed two
     simultaneous requests could pass the count check simultaneously -
     SQLite's global write lock masked this.
  b. FK ENFORCEMENT TIMING: SQLite FKs can be deferred; PG checks immediately
     unless deferred. onDelete: Cascade/SetNull semantics are preserved by
     Prisma on PG, but deletion error codes/messages differ (P2003 vs P2002).
  c. CASE SENSITIVITY: SQLite LIKE is case-insensitive for ASCII; PG LIKE is
     case-sensitive. The codebase currently does NO DB-level contains/text
     search (all case folding happens in JS), so no breakage found - but any
     future "contains" filter must add mode: 'insensitive' on PG.
  d. STRING ORDERING / COLLATION: SQLite uses binary (byte-wise) ordering; PG
     uses the database collation (e.g. en_US.UTF-8). Any UI relying on exact
     orderBy of name/email/key strings may order differently.
  e. INTEGER ID REUSE: after deletes SQLite can reuse rowids; PG sequences
     never go backwards. Seed/purge demo cycles will produce monotonically
     increasing ids.
  f. TIMESTAMP PRECISION: Prisma PG uses TIMESTAMP(3) (millisecond, stored
     UTC); SQLite stored full-precision strings. All Date math is JS-side
     (Date.now(), toISOString()), so no breakage, but sub-ms data is
     truncated on import.
  g. CONNECTION LIFECYCLE: a long-running Express process now holds pooled
     TCP connections - needs connection_limit sizing vs. Supabase pooler
     limits; introduces network latency and possible transient errors where
     SQLite was in-process (startup ensureTeams/bootstrap in server.js now
     depends on network availability).
  h. groupBy/count semantics are identical via Prisma; there are NO JSON
     columns (all JSON-as-string), so no JSONB decisions required.

  copy is safe and read-only with respect to the DB engine). Never delete it -
  it is the rollback source of truth.
- ID PRESERVATION: every table uses Int autoincrement PKs and cross-references

  be imported WITH ORIGINAL IDS, then every PostgreSQL sequence must be
  advanced (setval) past the max id - including the special TicketSequence row

  Ticket.ticketNumber, Ticket.graphMessageId, Comment.graphMessageId,

  respect FKs (Agent/Team before Ticket/TeamMembership, ...) or load with FKs
  deferred/disabled then validate.
- BOOLEANS are stored as 0/1 in SQLite; a proper migration path (pgloader or
  a script through Prisma) converts them. Do not copy raw SQL by hand.
- DATETIME: verify NULL handling on the many nullable date fields
  (resolvedAt, closedAt, dueAt, expiresAt, queuedAt, pausedAt, remainingMs,
  lastRenewedAt, lastAssignedAt). remainingMs Int? carries handover pause
  state that must not be recomputed.
- GraphSubscription state: import as-is so a restarted server renews the live
  subscription rather than orphaning it.
- RECOMMENDED TOOLING: pgloader (SQLite->PG in one shot; handles type/boolean
  coercion + sequences) OR a Node script reading the SQLite DB via a temporary
  sqlite-provider schema copy and writing via the postgres client in
  dependency order. Prisma Migrate alone does NOT move data.
- CUTOVER WINDOW: pause email ingestion and the app during the copy to avoid
  split-brain writes; keep the SQLite path intact until cutover is verified,
  then leave dev.db archived.

6. RECOMMENDED SUPABASE CONNECTION CONFIGURATION
--------------------------------------------------------------------------------

schema.prisma:
  datasource db {
    provider  = "postgresql"
    url       = env("DATABASE_URL")   // pooled, for the app at runtime
    directUrl = env("DIRECT_URL")     // direct, for migrate / db push / shadow
  }

- DATABASE_URL (app runtime, long-lived Express process): the Supabase
  SESSION pooler (port 5432 on the pooler host,
  aws-0-<region>.pooler.supabase.com, user postgres.<project-ref>).
  The TRANSACTION pooler (port 6543, ?pgbouncer=true&connection_limit=...)
  is only required for serverless / many short-lived connections; a
  persistent Node server is better on session mode. Include
  ?connection_limit=N sized to the Supabase plan.
- DIRECT_URL: the DIRECT connection (db.<project-ref>.supabase.co:5432,
  user postgres) - required because Prisma Migrate needs DDL and a shadow
  database, which poolers do not support.
- URL STRUCTURE: postgresql://<user>:***@<host>:<port>/postgres
  - passwords contain special characters and MUST be URL-encoded.
- TESTS (testdb.js) should get their own separate Supabase project/branch or
  dedicated database so suites can push/drop freely without touching
  production data.
